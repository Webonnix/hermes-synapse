# Разбор nesquena/hermes-webui и что из него взять в HERMES/Vexa

Дата: 2026-09-12. Источник: клон `master` (~8k коммитов, 18.3k звёзд, MIT, создан 2026-03-30,
последний push 2026-09-12). Это **другой** Hermes — веб-UI для Hermes Agent от Nous Research,
не связан с нашим проектом кодом, только предметной областью.

## 1. Что это такое на самом деле

| Параметр | hermes-webui | Наш проект |
|---|---|---|
| Бэкенд | Python stdlib `ThreadingHTTPServer`, роутинг через `if/elif` | FastAPI + async, ~70 модулей |
| Фронтенд | vanilla JS, без сборки и бандлера | React 19 + TS + Vite, code splitting |
| Транспорт | SSE (несколько потоков) | один WebSocket `/api/ws` |
| Крупнейший файл | `api/routes.py` — **1.3 МБ**, `static/ui.js` — **1.0 МБ** | `backend/main.py` — 5224 строк |
| Тесты | ~1150 файлов pytest | 89 файлов / 1322 теста + 30 frontend-тестов |
| Состояние | JSON-сайдкары в `~/.hermes/webui/` + чужая `state.db` | SQLite `hermes.db` |
| Открытых issue / PR | 850 / 578 | — |

**Вывод по архитектуре: копировать код не надо.** Наш стек объективно лучше:
модульный async-бэкенд против одного 1.3-мегабайтного файла с `if/elif`-диспетчером,
типизированный React с ленивой загрузкой против мегабайтного `ui.js`, нормальная БД
против JSON-файлов с `.bak`-снапшотами. Репозиторий очевидно писался агентами на скорость,
отсюда 850 открытых issue.

**Но ценность в другом.** Они прошли через 6 месяцев эксплуатации у тысяч самохостеров
и решили ровно тот класс проблем, который у нас регулярно всплывает: обрывы стрима,
падения без следов, потеря хода после рестарта, публичные ссылки без утечек, мобильный доступ.
Ниже — только то, что реально применимо.

## 2. P0 — то, что закрывает наши повторяющиеся баги

### 2.1. WebSocket: широковещание без адресации, без seq, без replay

`backend/websocket_manager.py` — 41 строка: один `Set[WebSocket]`, `broadcast()` рассылает
**каждое** сообщение **всем** подключённым сокетам. 31 место в бэкенде зовёт `manager.broadcast`.
`chat_id`/`run_id` в payload есть, но фильтрует их только фронтенд.

Две независимые проблемы:

1. **Безопасность/мультиарендность.** Токены доступа ботов, CRM-клиенты, биллинг —
   а токены чата любого агента прилетают в каждую открытую вкладку. Сервер не проверяет,
   имеет ли эта сессия право видеть этот `chat_id`.
2. **Надёжность.** `App.tsx:1266` — переподключение через `setTimeout(connectWS, 3000)`
   вслепую. Всё, что стримилось в течение разрыва, теряется навсегда.
   Это буквально класс багов из наших заметок: «оркестратор онемел», «ответ появился
   только после перезагрузки», «пустой ответ».

Как решено у них (`docs/sse-streams.md`, `docs/rfcs/session-sse-contract-v1.md`):

- каждое событие несёт `id: <stream_id>:<seq>`;
- клиент переподключается с курсором `after_event_id` / `after_seq` (fallback — стандартный
  заголовок `Last-Event-ID`);
- если in-memory стрима уже нет — отдаётся **реплей из run-журнала** на диске;
- невалидный/чужой/забежавший вперёд курсор трактуется как «реплей с начала»,
  а не как «молча пропустить события»;
- heartbeat каждые 5 с и `X-Accel-Buffering: no`, чтобы nginx не буферизовал.

**Что делать у нас** (WebSocket менять не нужно):
- добавить в `ConnectionManager` карту `websocket -> set(subscribed_chat_ids)` и
  `send_to_chat(chat_id, msg)` вместо `broadcast`; `broadcast` оставить только для
  реально глобальных событий (`settings_update`, `config_update`);
- добавить монотонный `seq` на `run_id` и кольцевой буфер последних N событий рана
  (N ≈ 500) в памяти;
- при реконнекте клиент шлёт `{type:"resume", run_id, after_seq}`, сервер досылает хвост;
- экспоненциальный backoff вместо фиксированных 3 с.

Ориентировочно 150–200 строк, и целый класс «немых ответов» закрывается.

### 2.2. Write-ahead журнал хода (turn journal)

`api/turn_journal.py` + `docs/rfcs/turn-journal.md`. Идея: **до** того, как пойдёт работа
провайдера, сообщение пользователя дописывается в append-only журнал. Дальше журнал
двигается по статусам. После краша восстановление детерминировано, а не «догадаемся
по pending_user_message и .bak».

У нас в `docs/product-and-architecture-audit.md` уже записаны `agent_runs` и `trace_spans`
в P1 — это ровно та же потребность, но журнал ещё и решает **потерю хода при рестарте
контейнера**, а не только наблюдаемость. У нас SQLite, так что JSONL не нужен:
таблица `run_events(run_id, seq, ts, kind, payload)` + `runs(status, …)` закрывает
одновременно 2.1 (реплей), 2.2 (восстановление) и P1-аудита (трейсы).

### 2.3. Видимость падений

`api/crash_visibility.py` (301 строка, читается за 5 минут). Их наблюдение: демон-поток
умирает — в логе обрыв на середине запроса, ни трейсбэка, ни строки о завершении.
Решение: `faulthandler.enable()`, свой `threading.excepthook` и `sys.excepthook`
в логгер, аудит-строка при штатном завершении. Правило: хук **никогда не бросает
исключение**, иначе сам становится новым молчаливым сбоем.

У нас в одном FastAPI-процессе живут scheduler, Telegram/Matrix/Discord-боты, dev-runs,
price_monitor. Тихо умерший `asyncio.Task` — наш штатный режим отказа.
Минимум: `faulthandler.enable()`, `loop.set_exception_handler(...)` и обёртка
`create_task`, которая логирует исключение задачи вместо его проглатывания.

### 2.4. Watchdog медленных запросов

`api/request_diagnostics.py`. При превышении порога (5 с) дампятся стеки всех потоков
для зависшего запроса. Важная деталь из их же комментария: первая версия делала
`threading.Timer` на **каждый** запрос — под нагрузкой от поллинга `/api/sessions`
процесс упёрся в лимит потоков (`can't start new thread`) и перестал принимать соединения.
Переделали на **один** глобальный watchdog-поток.

У нас дашборд поллит много эндпоинтов; ту же ошибку легко повторить.

## 3. P1 — функциональность, которой у нас просто нет

### 3.1. Публичные read-only ссылки на диалог

`api/shares.py` (523 строки), эндпоинты `POST /api/share/create`, `POST /api/share/revoke`,
`GET /share/<token>`. Ключевое — это **не** «отдать сессию по ссылке», а
**иммутабельный санитизированный снапшот**:

- отдельная, намеренно более узкая форма, чем полный экспорт;
- редактирование локальных путей (`_redact_share_paths`);
- картинки встраиваются внутрь, SVG санитизируется (`_sanitize_svg_bytes`),
  MIME проверяется по magic bytes, а не по расширению;
- нет workspace, профиля и сырых tool-payload'ов;
- отзыв ссылки.

Нам это прямо в тему: у нас есть публикация демо в `/demo/`, и уже была утечка
`.git` (с URL Gitea-ремоута) в публичный неаутентифицированный путь.
Модель «снапшот + санитизация + отзыв» безопаснее, чем симлинк на рабочую директорию.

Рядом — `api/session_export_html.py`: один самодостаточный HTML-файл без CDN и внешних
ассетов, открывается офлайн двойным кликом. Дешёвая и приятная фича для отчётов клиентам.

### 3.2. PWA / service worker

`static/sw.js` + `manifest.json`. У нас этого нет вообще (`grep serviceWorker` — пусто),
хотя Vexa задумана в том числе как телефонный интерфейс.

Их решения, которые стоит скопировать один в один:
- имя кэша со **версией, подставляемой сервером из git-коммита** — ручные бампы не нужны;
- в precache попадают только версионированные ассеты с тем же `?v=`, что шлёт страница,
  иначе каждый lookup промахивается;
- старые кэши удаляются **до** открытия нового (квота);
- `/` и логин-ассеты намеренно **не** предкэшируются: под паролем ответ бывает то шеллом
  приложения, то страницей логина, и протухший кэш ломает вход.

Учитывая нашу историю со «старым бандлом после деплоя» — SW, сделанный неправильно,
усугубит проблему, сделанный правильно (версия из коммита + прунинг) — снимет её.

### 3.3. Аутентификация: passkeys и OIDC

`api/passkeys.py`, `api/auth_oidc.py`. Подписанная HMAC HttpOnly-кука на 24 ч,
пароль как bootstrap/recovery-путь, после регистрации хотя бы одного passkey можно
удалить пароль. Плюс security-заголовки на всех ответах и лимит тела POST в 20 МБ.

У нас пароль + Cloudflare Access. Passkeys сняли бы зависимость от CF Access
для телефона (в заметках: публичный домен за SSO, API-клиентам нужен Service Token).
Их же предупреждение стоит учесть: PKCE/state у них в памяти процесса, за балансировщиком
нужен sticky-session.

### 3.4. Экспозиция себя как MCP-сервера

`mcp_server.py` (25 КБ) — WebUI отдаёт себя как MCP-сервер, чтобы другой агент мог им управлять.
У нас есть `mcp_client.py` и `mcp_openapi_proxy.py` — только потребление.
Обратная сторона позволила бы Claude Code / Cline дёргать наших агентов, dev-runs и CRM напрямую.

### 3.5. Медиа-снапшоты

`api/media_snapshots.py`. Проблема: `/api/media` отдаёт **текущие** байты файла, поэтому
перезапись `report.html` переписывает и все исторические превью в чате — пользователь
теряет сравнение «было/стало». Решение: при закрытии хода байты каждого локального файла
из сообщения фиксируются в content-addressed хранилище.

У нас dev-runs и content-factory генерируют артефакты итеративно под теми же именами —
ровно тот же баг.

## 4. P1 — процесс и эксплуатация (самое дешёвое по усилию)

### 4.1. `AGENTS.md` в корне репозитория

У нас `.agents/` и `.codex/` **пустые**, `CLAUDE.md` нет. При этом весь рабочий процесс —
агентский, а десятки выстраданных правил (app_settings с двойной кодировкой; модель нужно
менять в 4 местах включая `src/.env`; `num_batch` должен совпадать во всех контейнерах;
прод не равен репозиторию; тесты гонять в одноразовом контейнере, не в живом бэкенде)
живут только в памяти Claude и недоступны ни Codex, ни Cline, ни новой сессии без памяти.

Их `AGENTS.md` — хороший шаблон: «читай сначала это», список контрактов по подсистемам,
правила безопасности локального прогона (изолированный `HERMES_HOME` для экспериментов,
не печатать ключи и `.env`), стиль PR.

### 4.2. `docs/GUIDELINES.md` — 10 правил

Это лучший артефакт репозитория, и он почти дословно описывает наши собственные разборы:

1. Чини **класс** бага, а не экземпляр — у бага есть братья в других вызовах.
2. Проследи одно авторитетное значение end-to-end (`вход → нормализация → решение → действие
   → persist → cleanup`); тот, кто **решает**, и тот, кто **делает**, обязаны использовать
   одно и то же разрешённое значение. — Это ровно наш баг «endpoint и model разъехались
   в 4 местах → HTTP 404».
3. Не можешь подтвердить — **падай закрыто** и скажи об этом. «Неизвестно» ≠ «разрешено».
4. Перечисли пространство состояний до правки: 0/1/много, все выходы жизненного цикла
   (успех/ошибка/отмена/замена/teardown), auth on/off, конкурентность, враждебный ввод.
5. Считай вход враждебным; проверяй в точке использования (держи handle, не перерезолвливай путь).
6. Тест обязан **падать до** фикса и проходить после.
7. У каждого куска состояния есть владелец; докажи освобождение на **каждом** выходе.
8. Fallback'и и дефолты — это контракт: расширяй механизм, не копируй его.
   Одинаковая правка в N параллельных блоках = ты не нашёл узкое место
   (пример: новая строка ушла только в локаль `en`).
9. Диф — это задача и ничего больше.
10. Видимый контрол стоит внимания при каждом визите: размещай по частоте использования.

Предлагаю положить сокращённую версию в наш `CLAUDE.md`/`AGENTS.md`.

### 4.3. `docs/CONTRACTS.md` + `docs/rfcs/`

Индекс «подсистема → контракт», который агент обязан прочитать перед правкой. У них
11 RFC (SSE-контракт, turn journal, разделение исходников агента, консистентность
run-state). У нас неявных контрактов не меньше, и каждый раз они всплывают через
инцидент.

### 4.4. CI

У нас один workflow `test.yml`: pytest + lint + vitest + build. У них семь:
`tests.yml` (шардированный pytest + быстрый путь для docs-only изменений),
`browser-smoke.yml`, `docker-smoke.yml`, `conversation-lifecycle.yml`,
`docs-ci.yml`, `native-windows-startup.yml`, `release.yml` (multi-arch + GitHub Release).

Нам конкретно не хватает двух:
- **docker-smoke**: поднять compose, дождаться healthcheck, `curl` главную и один API-путь.
  Поймал бы и «пустой экран из-за незащищённого list-состояния», и «старый бандл»,
  и `npx tsc --noEmit ≠ сборка образа».
- **browser-smoke**: Playwright открывает `/`, проверяет, что `#root` не пустой.
  Это буквально наш чеклист диагностики белого экрана, только автоматически.

Полезная деталь их `tests.yml`: детектор «изменения только в документации» **не может
упасть** — он всегда `exit 0` и всегда пишет `docs_only` (по умолчанию `false`),
потому что упавший job сделал бы обязательные проверки `skipped`, а PR — вечно pending.

### 4.5. `ctl.sh` и скрипты-аудиторы

`ctl.sh` (31 КБ) — `start/stop/status/logs` с проверкой, что PID действительно **наш**
процесс (`_is_owned_webui_pid`), диагностикой «кто занял порт», обнаружением конфликта
с systemd-юнитом и предупреждением «на порту отвечает неуправляемый инстанс».

Учитывая наши инциденты (сеть после ребута, прод дрейфует от репозитория,
«деплой ничего не изменил») — стоит дописать `deploy/hermes-compose-up.sh` до
`ctl.sh`-подобного: `status` с проверкой версии бандла на проде и
скрипт `audit_prod_drift.sh`, который md5-дифает деревья (сейчас мы это делаем руками).
Аналог у них — `scripts/audit_agent_source_dependencies.py`.

### 4.6. `scripts/test.sh`

Тесты гоняются только через скрипт: он создаёт/использует `.venv`, жёстко ограничивает
интерпретатор Python 3.11–3.13 и доставляет dev-зависимости. В `AGENTS.md` прямо написано:
«если прямой вызов pytest жалуется на интерпретатор — перезапусти через `./scripts/test.sh`,
прежде чем дебажить продуктовый код».

У нас правило «собирать и тестировать в контейнере `node:20` (Debian, не alpine),
потому что хостовый node v12 непригоден» существует только в памяти. Оно должно быть
скриптом в репозитории.

## 5. P2 — продуктовые фичи чата, которых нам не хватает

Отсортировано по соотношению «польза / трудозатраты»:

1. **Индикатор контекста в композере** — токены, стоимость, полоса заполнения с учётом
   модели. У нас уже есть tok/s и разбивка под ответом; это — вторая половина.
2. **Очередь сообщений во время генерации** — отправленное во время работы агента
   встаёт в очередь, а не блокируется.
3. **Редактирование прошлого сообщения пользователя с регенерацией с этой точки.**
4. **Slash-команды с автодополнением**: `/model`, `/compress [тема]`, `/theme`, `/usage`,
   `/new`, `/workspace`. Нераспознанная команда просто уходит агенту.
   У нас есть condenser — `/compress` даёт ему ручной вход.
5. **Карточки tool call** с именем, аргументами, обрезанным результатом и
   «свернуть/развернуть всё» для многоинструментных ходов; отдельная иконка и отступ
   для делегирования субагенту. У нас делегирование есть, визуализации хода — нет.
6. **Сворачиваемые карточки reasoning/thinking.**
7. **Карточка апрува опасной команды**: разрешить один раз / на сессию / всегда / запретить.
   У нас есть `approval_dispatch` — не хватает именно UI-гранулярности «на сессию».
8. **Сессии**: закрепление, архив, проекты с цветами, теги `#tag` из заголовка с
   фильтром по клику, группировка Today / Yesterday / Earlier.
   Проекты у нас уже есть, остальное — дешёвая надстройка.
9. **Панель Todos** — живой список задач из tool-состояния текущей сессии
   (`api/todo_state.py`: live через SSE + «холодная» загрузка из последнего `role=tool`
   сообщения, обе ветки через один нормализатор — хороший приём).
10. **Скины через `data-skin` + CSS-переменные** (у них 11 штук поверх system/dark/light).
    У нас `vexa.css`; такой разрез делает новую тему делом 30 строк переменных.
11. **Встроенный терминал** (`api/terminal.py`) — с явным cwd/env на процесс и без мутации
    глобального `os.environ`.
12. **Mermaid и KaTeX инлайн**; кнопка копирования кодоблока.
13. **Голосовой ввод через Web Speech API** — кнопка микрофона, живая промежуточная
    расшифровка, автостоп после ~2 с тишины. У нас XTTS/Vexa уже есть, но это — дешёвый
    путь ввода в обычном чате без GPU.

## 6. Чего у них нет, а у нас есть

Чтобы калибровать: наш проект содержательно глубже по продукту — мультиагентность с
бюджетами и тарифами, per-agent мессенджеры (Telegram/Discord/Matrix/VK/WhatsApp/Slack/email),
CRM с клиентами и сделками, биллинг и крипто-подписки, content-factory и SMM,
автономные dev-runs с песочницей, 9Router с fallback-цепочками, RAG/Obsidian,
governance инструментов и провайдеров. Ничего из этого в hermes-webui нет.

Мы берём у них **не функциональность продукта, а инженерную зрелость носителя**:
durability, восстановление, наблюдаемость, безопасная публикация, мобильный доступ,
дисциплина документации и CI.
