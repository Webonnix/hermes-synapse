# Разбор аудита Hermes и первый этап исправлений

Дата: 30 октября 2026. Источник: предоставленный PDF «Hermes: аудит архитектуры,
AI и DevSecOps», 10 страниц. Проверенная база: `feat/agent-runtimes`, `4b68a62`.
Рекомендации документа рассматривались как предмет проверки; команды из него
не выполнялись автоматически. Рабочий прод, его переменные окружения, доступность
из интернета и содержимое пользовательских данных не проверялись.

## Вывод

Основная проблема описана верно: независимые защитные механизмы не составляют
сквозную границу доверия. Скомпрометированный вход даёт права владельца;
режим full снимает подтверждения; доступ к Docker API позволяет выйти за границы
песочницы. Privacy gateway защищает исходящий текст только при выполнении своего
контракта, а при ошибке локального детектора по умолчанию разрешает отправку.

Начат ограниченный, проверяемый этап: защита входа (C1/C2 и перебор пароля).
Остальные изменения требуют отдельных проверок и не считаются выполненными.

## Проверка критических замечаний

| ID | Что найдено в исходниках до правки | Статус после первого этапа |
| --- | --- | --- |
| C1 | `backend/auth.py`: неограниченные проверки OTP, сравнение через `==`, код ещё действовал на точной границе expiry | Исправлено для текущего однопроцессного API: 5 попыток, одноразовость, constant-time comparison, точная граница TTL, блокировка конкурентного доступа |
| C2 | `backend/main.py`: выпуск кода до проверки Telegram; каждый запрос заменял OTP и инициировал отправку | Исправлена неограниченная рассылка и замена живого кода: cooldown, 429, rate limit, отзыв при ошибке/отмене доставки. Публичный запрос кода и риск временного отказа во входе остаются |
| C3 | `active_sessions` — множество в памяти без TTL; токен записывается в localStorage; в nginx нет CSP/HSTS | Открыто. Добавлен только no-store на auth-ответы бэкенда. Это не замена TTL, cookie, CSRF и серверному отзыву |

| C6 | `privacy/config.py` выбирает open по умолчанию; `privacy/gateway.py` после ошибки локального прохода продолжает с regex и частичными находками | Небезопасный fallback подтверждён кодом. Конкретное значение на проде не проверено; утверждение PDF о продовом .env отдельно не подтверждено |

Дополнительная находка: публичный `/api/auth/login` позволял неограниченно
проверять пароль и запускать PBKDF2. Теперь он ограничен до дорогой проверки.

## Что изменено в первом этапе

### OTP и конкурентность

- Срок действия 300 секунд измеряется монотонными часами; изменение системного
  времени не продлевает жизнь кода.
- Пять неверных проверок аннулируют код. Пятый правильный ввод допускается;
  повторное применение успешного кода запрещено.
- Действующий код не заменяется и не отправляется повторно даже после 60 секунд.
  Новый можно запросить после expiry, либо после отзыва и истечения cooldown.
- Общая блокировка защищает выдачу, проверку, отзыв и квоты. Одновременные
  запросы не выпускают несколько кодов и не дают два успешных использования.
- Неверный Unicode-ввод безопасно отклоняется; сохраняется совместимость
  с пробелами вокруг кода.
- До выпуска проверяется наличие получателя и бота. Ошибка либо отмена доставки
  отзывает соответствующий код, сохраняя паузу перед следующей отправкой.
- В лог ошибки Telegram записывается только класс исключения. Тело исключения
  может содержать чувствительные данные и больше не выводится этим обработчиком.

### HTTP и reverse proxy

| Защита | Значение |
| --- | --- |
| OTP-попытки | 5 на код |
| Выпуск нового OTP | Не чаще раза в 60 секунд; живой код не заменяется |
| request-code, бэкенд | 10 запросов за скользящие 60 секунд на процесс |
| verify-code, бэкенд | 20 запросов за скользящие 60 секунд на процесс |
| password login, бэкенд | 5 запросов за скользящие 60 секунд на процесс |
| nginx `/api/auth/` | 10 запросов/мин на непосредственный peer, burst 10 |
| Отказ по лимиту бэкенда | 429, Retry-After, Cache-Control: no-store |
| Размер полей | OTP ≤64, username ≤256, password ≤4096 символов; те же границы при изменении учётных данных |

Квоты независимы для трёх способов обращения: перебор пароля не расходует
бэкенд-квоту OTP. Невалидное тело запроса расходует квоту до Pydantic;
OPTIONS не расходует. nginx добавляет общую внешнюю защиту auth-префикса.

Лимиты бэкенда намеренно не зависят от X-Forwarded-For: произвольный заголовок
не покупает новые попытки, распределённый перебор не обходит общую квоту,
не создаётся неограниченный словарь адресов. Обратная сторона — злоумышленник
может временно исчерпать общую квоту владельца. За reverse proxy квота nginx
тоже может быть общей. Доверие к реальному адресу клиента требует отдельной
настройки списка доверенных прокси, а не доверия любому заголовку.

## Уточнения к остальным выводам аудита

### Публичные ссылки и изображения

`backend/shares.py` уже публикует только user/assistant и поля role/content/ts,
исключает system/tool, чистит распознаваемые credentials и локальные пути.
Это подтверждает существование защиты, но не доказывает отсутствие PII,
плейсхолдеров или системных инструкций, повторённых в assistant.content.
Нужны негативные тесты именно такого текста. Полностью закрыть `/share/`
обычной сессией означало бы изменить сам контракт публичной ссылки.

`/api/generated-images/` действительно исключён из обычной аутентификации.
Следующий шаг: каталог артефактов с владельцем, сроком и назначением ссылки;
подпись должна включать идентификатор и срок действия. Проверить также `/api/plots/`
и все существующие способы показа изображений, иначе защищается только один путь.

### Контейнеры и воспроизводимость

Не все образы плавающие: в compose уже закреплены digest для Docker proxy,
OmniRoute, Qdrant, llama.cpp; uv в Dockerfile тоже закреплён. При этом базовые
python/node/nginx используют теги. Точные версии Python-зависимостей уже
устанавливаются из uv.lock с проверкой хешей. Следовательно, усиление supply chain
нужно продолжить поверх существующего механизма.

Для non-root потребуется проверить права всех записываемых каталогов и bind
mount, загрузку моделей, медиа, git и создание песочниц. read_only требует явных
томов и tmpfs. Эти флаги без инвентаризации легко ломают запуск, а полномочия
Docker API сохраняются независимо от UID процесса.

Утверждение о ручной сборке прода из нескольких веток из локального кода не
проверяется. В рабочем каталоге действительно несколько checkout с разными HEAD;
в соседнем src есть незавершённые изменения. Это не доказательство их выкладки.
Нужен отдельный снимок развёртывания: image digest, compose hash, commit и настройки
без секретов. Текущую работу в src и openbot_local этот этап не меняет.

### AI и очередь

В compose llama.cpp задан parallel=1. Это подтверждает ограничение локальной
конкурентности, но степень конкуренции за GPU требует замеров очереди и задержек.
Перенос фоновых задач во внешний LLM зависит от бюджета, политики приватности
и качества; считать его универсальным безопасным fallback нельзя.

Evals нужны на маршрутизацию, PII, выбор инструментов и оценку Earner. Проверка
должна охватывать всю связку model + prompt + generation parameters + endpoint.
Одного поля model недостаточно: тот же id может обслуживаться другой версией.
Первый набор должен быть детерминированным и без внешних side effects; реальные
измерения качества/стоимости запускать отдельно с явным лимитом бюджета.

### Интерфейс и границы модулей

Предложение объединить экраны вокруг сущностей разумно, но перенос навигации
следует делать с сохранением старых hash/deep links и адресной WebSocket-доставки.
Карточка агента, список запусков и центр подтверждений должны использовать
канонические данные, а не создавать параллельные состояния в новых экранах.

Разделение API, workers, каналов и телефонии имеет смысл после определения
контракта заданий: durable status, lease, идемпотентность, retry и dead-letter.
Нельзя просто запустить несколько копий нынешнего процесса: OTP/сессии находятся
в памяти, а фоновые обработчики могут стартовать несколько раз. Выбор конкретной
очереди должен следовать этому контракту; набор названий технологий его не заменяет.

## Следующие этапы и критерии приёмки

1. **C3: единая аутентификация.** Valkey TTL 12 часов и idle timeout,
   случайный session id с серверным хранением, HttpOnly/Secure/SameSite cookie,
   CSRF на изменяющих запросах, logout/revoke, смена пароля с отзывом сессий.
   OTP и rate limit перенести атомарно в то же общее хранилище. Проверить REST,
   WebSocket, десктопный VNC, загрузки и все проверки ролей. Истёкшая сессия
   должна терять доступ и на уже открытом соединении. Ошибка Valkey не даёт доступ.
2. **C5: серверная граница автономии.** Сначала временное ограничение full
   на сервере и в интерфейсе; затем durable provenance для web/MCP/DOM/входящих,
   наследование в делегировании, истории и сжатии. Недоверенный контекст требует
   подтверждения исходящих действий при любом режиме. Проверять также shell,
   сохранённые задачи и уже выданные approvals: смена режима не снимает этот gate.
   Повторная аутентификация защищает повышение автономии и критические approvals.
3. **C6: защищённый внешний вызов.** Закрытый отказ при неполной проверке
   приватности; явная политика по источнику данных и границе провайдера.
   Тест с отказавшим детектором обязан доказать отсутствие HTTP-запроса наружу,
   включая fallback и streaming. Локальная генерация должна оставаться доступной.
4. **C4: ограниченный sandbox-launcher.** Allowlist digest/runtime/network,
   запрет privileged/host namespaces/произвольного bind. Бэкенд не получает общий
   Docker API; non-root, capabilities и read_only проверяются отдельным smoke-тестом.
5. **CI и развёртывание.** Проверка секретов/SAST/SCA, lockfiles, evals,
   сканирование и SBOM, сборка и подпись. Деплой принимает проверенный digest,
   делает бэкап, readiness и автооткат. Сначала зафиксировать фактический прод;
   не выкладывать ветку поверх неизвестного набора локальных изменений.
6. **Наблюдаемость и подтверждения.** Сквозной trace_id и безопасные метаданные,
   единый список approvals с предпросмотром получателя/diff/суммы, аудит решений.
   Обучаемые правила первоначально только предлагаются владельцу; положительные
   одобрения не должны автоматически расширять разрешения заражённого контекста.
7. **Модульность и UX.** Последовательно выделить workers/каналы/телефонию,
   затем навигацию по сущностям. До миграции БД проверить существующую абстракцию
   PostgreSQL в database.py, модель конкурентных записей и восстановление бэкапов.

Не проверены: реальные сетевые экспозиции и порты, конфигурация прода, работоспособность
offsite backup/restore, юридическое соответствие клиентского развёртывания и полный
список всех маршрутов на предмет обхода авторизации. Внешние сканеры и нагрузка на
публичный сервер не запускались.

## Проверки первого этапа

Регрессионные тесты `test_auth_security.py` сначала запущены на старом коде:
11 падений и 3 успешных проверки. Среди воспроизведённых дефектов: правильный
код принимался после пяти ошибок, 16 конкурентных запросов выпускали 16 кодов,
код принимался на точной границе expiry. После исправления проходят все 14.

`test_auth_http.py` проверяет настоящий ASGI middleware и маршруты с ботом-заглушкой:
429/Retry-After/no-store, одноразовость, exhaustion, невалидные тела, поддельные IP,
password hashing budget, отсутствие конфигурации, ошибку и отмену доставки.
Проверки выполняются в отдельной копии исходников в /tmp без .env и рабочей БД.

Итоговые проверки:

| Проверка | Результат |
| --- | --- |
| OTP, HTTP-вход, исходный auth-flow, роли Clients/Inbox/Calendar/CRM | **90 passed**, Python 3.11.15, зависимости из uv.lock, отдельные данные в /tmp |
| Новые проверки внутри этого набора | 14 unit + 11 HTTP, всего **25** |
| nginx smoke в одноразовом контейнере без сети | Конфигурация валидна; полный URI сохранён; 11 запросов пропущены, 12-й отклонён с 429 |
| Frontend lint, Node 20 Debian | Успешно |
| Frontend build (TypeScript + Vite) | Успешно; предупреждение о крупном JS chunk |
| Frontend Vitest | **419 passed, 1 failed**: `AgentDesktopsTab.test.tsx`, «sends a task to the chosen runtime»; ожидается opencode, отправляется пустой runtime. Исходники TS/TSX этого этапа не менялись |
| Полный backend suite | Успешный полный прогон **не получен**: остановлен лимитом 180 секунд после 1272 результатов. 17 падений в районе Content Factory в прогоне с временным Valkey; это окружение конфликтует с фикстурами, которые ожидают недоступный Valkey и подменяют только чтение. Эти падения нельзя выдавать за подтверждённые дефекты продукта |
| git diff --check | Успешно |

Зависимости Python 3.11 установлены из уже имеющегося кэша по lock-файлу;
для фронтенда использована копия существующего node_modules, без нового npm ci.
HTTP-тесты под ограниченной средой зависали на уведомлениях между потоками;
успешный прогон выполнен вне этого ограничения, по-прежнему в отдельной копии.
Никакие настоящие сообщения в Telegram и платные LLM-вызовы не выполнялись.
Временные nginx и Valkey контейнеры удалены.

Перед выкладкой нужен полный зелёный прогон в согласованном окружении:
зафиксировать недоступность Valkey во всех операциях fallback-тестов,
разобрать desktop runtime mismatch и проверить собранные образы на стейдже.
Описанная правка остаётся локальной; запуск и конфигурация продовых сервисов
не изменялись. Откат к старому auth-коду вернёт уязвимости C1/C2 и потому не
является безопасным способом отключить rate limit.
