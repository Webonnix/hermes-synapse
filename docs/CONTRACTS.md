# Контракты подсистем

Индекс неявных договорённостей, которые нельзя нарушить, не сломав что-то в
другом месте. **Прочитай раздел своей подсистемы до правки.** Каждый пункт здесь
появился после инцидента, а не из общих соображений.

---

## Вход и защита от перебора

Файлы: `backend/auth.py`, `auth_state.py`, `auth_http.py`, `main.py`,
`frontend/src/sessionAuth.ts`, `frontend/nginx.conf.template`.

- OTP: 300 секунд, один успешный обмен, не более пяти попыток; constant-time
  сравнение. Lua атомарно резервирует попытки и потребляет challenge в Valkey.
  Живой код не перезаписывается, cooldown 60 секунд сохраняется и при ошибке доставки.
- Rate limit до валидации тела и хеширования пароля: request-code 10, verify-code
  20, login/reauth/activity 5 за 60 секунд на установку. Поддельный forwarded IP
  не расширяет лимит. nginx дополнительно ограничивает непосредственного peer.
- Сессия: случайный непрозрачный id, в Valkey хранится его SHA-256-ключ, роль,
  CSRF nonce и expiry. Абсолютный TTL 12 часов, idle 30 минут. Поллинг и открытый
  WebSocket не продлевают idle; события пользователя и изменяющие запросы продлевают.
- Браузер: HttpOnly + Secure + SameSite=Strict cookie; id не возвращается в JSON
  и не читается JS. Отдельная читаемая cookie содержит только CSRF nonce.
  Изменяющие cookie-запросы требуют заголовок CSRF и допустимый Origin.
  Bearer остаётся для серверных клиентов и проверяется по тому же хранилищу.
- Logout отзывает сессию; смена пароля меняет общий epoch и отзывает все сессии.
  Повышение автономии, R4 approval и изменение browser login требуют свежего
  пароля (если настроен) + нового OTP, действительных пять минут.
- Ошибка Valkey — 503, без локального fallback. In-memory реализация включается
  только кодом из pytest conftest; переменной окружения для её включения нет.
  Общая auth state допускает несколько API-процессов; фоновые workers пока нельзя
  дублировать без durable lease. Старая сессия процесса после обновления не действует.
- Открытые WebSocket/VNC проверяют expiry/отзыв каждые пять секунд. Не-владельцы
  не получают глобальные config/log/chat события и не возобновляют чужие run streams.
- Неизвестные API по умолчанию owner-only. Ролевые домены имеют дополнительные
  проверки permissions. Auth и защищённые API несут no-store.

## Приватность и автономия

- Внешний текст проходит общий privacy gateway с закрытым отказом. `open` из
  старого env игнорируется. Отказ детектора/неполный проход не отправляет HTTP
  провайдеру; fallback может выбрать локальную модель.
- Локальность определяется разобранным hostname/IP, не подстрокой URL и не
  названием провайдера. Дополнительные локальные имена задаёт оператор через
  `HERMES_TRUSTED_LLM_HOSTS`; wildcard не используется. LlamaCppClient отказывает
  внешнему адресу. Sidecar браузера принимает только локальный LLM; legacy
  GraphRAG не посылает документы внешнему LLM. Непроверяемые изображения/аудио
  блокируются для внешних моделей, локальная мультимодальность сохраняется.
- Контекст без доказанного происхождения считается недоверенным. Чтение web,
  MCP, DOM, истории и делегирование не создают полномочий на исходящие действия.
  Режимы supervised/auto не могут снять нижний порог подтверждения R2/R3; R4
  требует двух подтверждений. Legacy full заменяется supervised и не выбирается.
- Approval связан с неизменными tool/arguments/requester. Claim задачи атомарен;
  повторное выполнение done возвращает прежний результат. Неудачный claim не
  меняет чужую running/rejected задачу. Более слабый principal не наследует approval.

## Сервис запуска песочниц

- Только `sandbox-launcher` видит Docker socket. Бэкенд использует ограниченный
  SDK-совместимый API; exec/build/pull/volume admin и чужие контейнеры недоступны.
- Launcher сам конструирует запуск: allowlist image ID, runsc, read-only root,
  фиксированный UID, cap_drop ALL, no-new-privileges, CPU/RAM/PID, quota. Входящие
  Binds — логические ссылки; daemon получает только subpath именованного volume.
  Произвольные host binds, host namespaces, privileged, devices и overrides запрещены.
- Подготовка данных идёт через удерживаемые directory fd и O_NOFOLLOW. Backend
  UID 10001, OpenBot home UID 1000; bootstrap передаётся отдельно от writable home.
- Данные мигрируются отдельно; Compose требует существующие external volumes,
  включая Valkey с ключом шифрования памяти. Preflight ничего не меняет и не
  печатает секреты. На машине без runsc запуск блокируется, runc fallback нет.
- Dev egress пока общий: per-agent/per-task proxy/domain ACL остаётся отдельным
  незакрытым пунктом. Сетевое ограничение нельзя считать выполненным по env proxy.

## WebSocket: адресная доставка и возобновление потока

Файлы: `backend/websocket_manager.py`, `backend/main.py` (`/api/ws`),
`frontend/src/wsResume.ts`, `frontend/src/App.tsx`.

- **Трафик чата адресный.** Используй `send_chat_event(chat_id, …)` или
  `send_run_event(run_id, chat_id, …)`. `broadcast()` — только для по-настоящему
  глобальных событий (`config_update`, `settings_update`, `logs_update`,
  `activity_log`). Событие чата, отправленное через `broadcast`, попадает во все
  открытые вкладки, включая чужие.
- **Ключ маршрутизации нормализуется в строку.** Часть продюсеров держит
  числовой chat_id (Telegram), а подписки приходят из JSON строками. Обе стороны
  приводятся к строке в `_chat_key`.
- **Каждое событие рана несёт монотонный `seq`.** Порядок в буфере совпадает с
  порядком отправки: `seq` резервируется и сериализуется **до** любого `await`.
- **Чанки потока — это дельты.** Применение одного и того же чанка дважды
  дублирует текст, поэтому клиент обязан отбрасывать `seq <= последнего
  применённого` (`RunCursorTracker.accept`).
- **Курсор, забежавший вперёд или чужой, — это `gap`, а не «нечего слать».**
  Ответ «нечего слать» молча проглотил бы реальные события. При `gap` сервер
  переигрывает всё, что ещё хранит, а клиент сбрасывает частичный текст рана.
- **Закрытый ран остаётся воспроизводимым `CLOSED_RUN_TTL` секунд.** Клиент,
  переподключившийся уже после завершения ответа, обязан его получить — именно
  этот случай раньше требовал перезагрузки страницы.
- **Совместимость по подпротоколу.** `hermes-v2` = адресная доставка + resume.
  Клиент на `hermes-v1` (устаревший бандл из кеша) получает старую
  широковещательную рассылку и пишет предупреждение в лог — деградирует, но не
  немеет.

## Входящие (Inbox), маршрутизация разговоров, внешний голос

Файлы: `backend/inbox.py`, `backend/inbox_rules.py`, `backend/inbox_routing.py`,
`backend/voice_providers.py`, `backend/inbox_api.py`; точки встраивания —
`bot_access_gate.authorize` / `record_turn`, `channel_replies`, `social_turn`,
все channel runtime'ы; фронтенд — раздел SMM Factory → «Диалоги»:
`frontend/src/components/smm/dialogs/DialogsSection.tsx` и остальное в `components/smm/dialogs/*`
(отдельной вкладки «Входящие» больше нет; `#tab=inbox` ведёт в SMM Factory → Диалоги).

- **Кто отвечает разговору — хранится в одном месте.** `handling` (`ai` / `human` /
  `blocked`) нигде не записывается: он вычисляется в `inbox.effective_handling` из
  `conversation_states.handling_mode` (перехват, ожидание) и последнего исхода правила.
  «Забрать диалог» в «Все диалоги» и ✋ в «Память агентов» (оба в SMM Factory → Диалоги) — один и тот же
  переключатель `owner_takeover`.
- **Архив ≠ память агента.** `inbox_messages` — то, что прошло по проводу (кто сказал,
  доставлено/черновик/отклонено/ошибка). `messages` — то, что читает модель.
  «Очистить переписку» стирает память и не трогает архив.
- **Любая запись в архив — best-effort.** Сбой архива не может стоить клиенту ответа:
  хуки глотают и логируют ошибки.
- **Повторная доставка события не исполняет ход второй раз.** Канал передаёт свой
  `event_id` в `authorize`; уникальный индекс `(conversation_id, external_event_id)`
  превращает редоставку в IGNORE ещё до вызова агента. Новый канал обязан передавать id.
- **Порядок решений в шлюзе:** дубликат → правило `block` → перехват → правило `pass` в
  рабочие часы → токены/подписки → меню/эскалация → маршрутизация. `block` сильнее
  токена; ошибка чтения правил не глушит всех (шлюз ниже сам контролирует доступ).
- **Рабочие часы влияют только на `pass`.** Пустое расписание = «часы не ограничены».
  Нераспознанное расписание не сохраняется.
- **Подсказка оператора (whisper) — только в system-сообщении следующего хода.** Никогда
  в user-сообщение и в `messages`. Внешнему голосовому агенту — только если у него есть
  отдельный канал инструкций (`config.supports_instructions`), иначе подсказка ждёт
  внутреннего хода. Ответ, дословно повторяющий подсказку, вычищается перед отправкой.
- **Маршрутизация разговоров ≠ AI Router.** `inbox_routing` выбирает *исполнителя* хода
  (агент или внешняя голосовая цель); модель для вызовов агента по-прежнему выбирают
  `local_orchestrator` + `router_tiers`. `human`/`blocked` до маршрутизатора не доходят.
  Ручной закреп сильнее авто и переживает перехват. Недоступная цель → политика
  `fallback_internal` (по умолчанию) / `fail_closed` / `human_takeover` — без исключений
  наружу.
- **WebSocket-кадры входящих несут только id.** `inbox_update {conversation_id, kind}` на
  ключ `inbox`; подписка на него режется сервером для роли без `inbox.view`. Текст
  клиент перечитывает через REST, где RBAC проверяется на каждом запросе.
- **Секреты внешних провайдеров — только в Valkey.** API отдаёт `has_secret`; ключи вида
  `*key*`/`*secret*`/`*token*` в `config` отклоняются. `base_url` проходит общий SSRF-валидатор,
  адрес перепроверяется после DNS на каждом вызове, редиректы не выполняются, у каждого
  вызова есть таймауты, повторы — только для GET. Webhook: HMAC-SHA256 по сырому телу,
  идемпотентность по `event_id`, одинаковый 401 для «нет провайдера / нет секрета /
  неверная подпись».
- **Медиа — ссылкой, не blob.** Аудио лежит в `DB_DIR/inbox_media/`, в SQLite — только
  `storage_ref`, отдаётся аутентифицированным `GET /api/inbox/attachments/{id}`.

## Телефония: звонки ИИ-агента

Файлы: `backend/phone_lines.py` (линии, звонки, провайдеры, подписи),
`backend/phone_service.py` (решение, сессии, вебхуки/медиа Twilio и Telnyx),
`backend/phone_asterisk.py` (ARI + RTP), `backend/phone_session.py` (цикл
разговора), `backend/phone_speech.py` (STT/TTS), `backend/phone_context.py` (контекст звонка
и телефонные инструменты), `backend/phone_api.py`; сайдкар `src/asterisk/`; фронтенд —
`components/smm/dialogs/PhonePanel.tsx`, `CallDialog.tsx`, `PhoneCallControls.tsx`
(SMM Factory → Диалоги → Звонки).

- **Звонок — это разговор во «Входящих»** на платформе `phone`: `binding_id` = id линии,
  `chat_id` = номер в E.164. Правила, рабочие часы, «Забрать диалог» и привязка к CRM
  работают без отдельной ветки. Метаданные звонка (длительность, отклик, причина конца)
  живут в `phone_calls`, текст — только в архиве.
- **Порядок решения на входящем:** линия выключена → лимит одновременных → правило
  `block` → правило `pass` (в часы, если задан номер владельца) → диалог забран владельцем →
  нет агента → ИИ. Тот же порядок для всех трёх провайдеров (`phone_service.inbound_decision`).
- **Ход агента по телефону** — обычный `_respond_as_subagent` внутри `CURRENT_CALL`:
  reasoning выключен (0.25 с до первого слова против ~3 с), ответ ограничен
  `PHONE_MAX_TOKENS`, телефонные инструменты предлагаются всегда, принципал —
  `public_channel`. Инструменты действуют только на *свой* звонок и отказываются вне звонка;
  `calendar_free_slots` отдаёт только свободные окна, не содержание встреч.
- **Перебивание — два действия:** отмена хода (токены и синтез больше не оплачиваются) и
  очистка очереди звука у транспорта. В архив попадает только то, что собеседник успел
  услышать, с пометкой `interrupted`, и это же сохраняется в память агента.
- **Отклик измеряется на каждом ходе** — от конца фразы собеседника до первого звука ответа;
  среднее и p90 хранятся в звонке. Это главная метрика качества.
- **Облачная речь с локальным резервом:** отказ STT до/во время звонка переключает на
  faster-whisper до конца звонка; отказ TTS до первого звука фразы — эту фразу говорит XTTS.
  Ключи — только в Valkey (`phone_speech_secret:*`, `phone_line_secret:*`).
- **Медиа Asterisk — RTP (μ-law, 20 мс), не AudioSocket.** В Asterisk 22.5.2 заголовок
  AudioSocket читается одним неблокирующим `read()`, и пустой сокет в момент чтения вешает
  звонок — на живом тесте он умирал в первую секунду. Адрес, куда слать наш RTP, приходит в
  `channelvars.UNICASTRTP_LOCAL_ADDRESS/PORT` ответа externalMedia; свой адрес бэкенд
  определяет маршрутом до хоста ARI (у бэкенда несколько сетей). Отправитель шлёт пакет каждые
  20 мс, тишину — когда нечего сказать.
- **Файл транков `data/asterisk/pjsip_trunks.conf` генерируется** (0600) и перечитывается
  через ARI; править руками бессмысленно. Несколько линий на одном SIP-сервере различаются
  по `line=yes` регистрации, а не по IP.
- **Публичные маршруты** `/api/phone/twilio/*` и `/api/phone/telnyx/*` проверяют подпись
  провайдера на каждом запросе; медиа-WebSocket открывается только с HMAC-токеном звонка,
  который бэкенд сам вложил в URL. Подпись Twilio считается от **публичного** URL из
  настроек, а не от внутреннего адреса запроса.
- **Покупка номера** выполняется только по явному `confirm: true` от человека (право
  `phone.manage`); у агента такого инструмента нет. Исходящий звонок из чата Vexa — R3.

## Саморазвитие агентов

Файлы: `backend/agent_learning.py`, `backend/agent_learning_api.py`; точки
встраивания — `rag.PRIVATE_SOURCES`, `obsidian.sync_vault_to_rag`,
`agent._respond_as_subagent` (`context_for_agent`), цикл в `main.py`.

- **Прогон — не цикл с инструментами.** Сбор → дедуп источников → один вызов LLM
  **без tools** с JSON-схемой → отброс несорсированного → скрининг инъекций →
  дедуп знаний → запись. Модель, которую может направить прочитанная страница, не
  должна уметь что-либо делать.
- **Веб-текст — данные.** Нормализуется (`clean_untrusted_text`: разметка,
  zero-width, управляющие символы, длина), подаётся в ограде с пометкой. Пункт с
  признаками обращения к агенту или со ссылкой не из собранных источников уходит в
  `quarantined`: не индексируется и не подмешивается, пока владелец не одобрит.
- **Провенанс — от сборщика.** URL пункта берутся по `source_ids` из собранного
  списка; пункт без валидного источника отбрасывается, а не «чинится».
- **Знания принадлежат агенту.** В Qdrant `source="agent_learning"` + `agent_id`.
  Поиск без явного `source_filter` их **не видит** (`rag.PRIVATE_SOURCES`) — иначе
  каждый прогон раздувал бы контекст всех агентов и Vexa. Граф GraphRAG их не
  индексирует (у графа нет владельца). Заметки `Hermes/Learning/` пропускаются
  синком хранилища — они уже проиндексированы поштучно.
- **Подмешивание ограничено:** не больше `CONTEXT_MAX_ITEMS` пунктов и
  `CONTEXT_MAX_CHARS` символов, порог `CONTEXT_SCORE`, с пометкой «не инструкции».
  Не зависит от `auto_rag` (тот про общий индекс документов) — отдельный
  `AGENT_LEARNING_CONTEXT_ENABLED`; иначе агент учился бы и никогда не пользовался.
- **Стоимость.** Модель агента; облачный провайдер — только пока у агента есть
  остаток бюджета, иначе локальная. Расход пишется в `decision_logs` под `agent_id`
  (только метаданные, без тела промпта). Лимиты прогона — источники, символы
  входа, токены выхода.
- **Расписание в БД, догон один раз.** `next_run_at = now + cadence` после
  прогона, не «предыдущий слот + cadence». Плановые прогоны — только в окне
  `AGENT_LEARNING_WINDOW`; нераспознанное окно = закрыто. Один прогон на процесс
  (`_RUN_LOCK`); ручной запуск при идущем прогоне — 409, не очередь.
- **Упавший прогон — один короткий ретрай.** `failed` ставит `next_run_at` через
  `min(cadence, FAILED_RETRY_HOURS)` (20 ч — то есть следующей ночью в окне), а не
  через неделю: обычно причина разовая. Второй `failed` подряд — снова полный
  cadence, чтобы не бить по сломанной модели каждую ночь. Источники упавшего
  прогона не помечены прочитанными, ретрай работает с теми же. `sources_count`
  пишется и для `failed` — сколько источников собрали до падения.
- **Выжимка без рассуждений.** Вызов идёт с `think=False`: локальная Qwen иначе
  наследует `LOCAL_THINK` чата и тратит весь `MAX_OUTPUT_TOKENS` на рассуждения —
  ответ «empty» (прод, 2026-10-17). Ключ читает только путь llama.cpp, облачный
  запрос его не получает.
- **Синки независимы.** Obsidian недоступен → знания уже в RAG, у прогона
  `note_pending=1`, следующий прогон трека дописывает заметку. Источники
  помечаются прочитанными только после успешной выжимки.
- **Сетевой доступ:** ленты — только из allowlist (`github.com` releases,
  OSV по нашим lockfile'ам); страницы из выдачи — только публичные адреса
  (`_assert_public_url`), без редиректов, ≤256 КБ. Произвольный URL ленты из API
  не принимается — новая цель egress это решение кода.
- Дефолтные треки сидятся `INSERT OR IGNORE` только для существующих агентов;
  правка владельца не перезаписывается.
- **UI** — блок «Саморазвитие» в карточке агента
  (`frontend/src/components/AgentLearningPanel.tsx`): треки, история прогонов,
  карантин и знания. 403 для не-владельца — тихая пометка, не ошибка; при
  идущем прогоне список обновляется сам раз в 5 с.

## DevSecOps-агент и аудит

Файлы: `backend/security_audit.py`; агент `devsecops` (сид в `database.py`,
дисциплина `security`), навык `security_audit`.

- **Только чтение и отчёты.** Четыре инструмента читают рабочий каталог
  (`autonomy.resolve_workspace`, в контейнере — `/workspace:ro`) и ничего не
  пишут и не исполняют. Риск R0, `security_audit_lockfiles` — R1 (наружу уходят
  имена и версии пакетов на `api.osv.dev`, больше ничего). Доступа к проду и SSH у
  агента нет; исправления — предложения владельцу или карточка канбана.
- **Секрет никогда не печатается.** Находка — файл, строка, правило и 8-символьный
  отпечаток sha256. `.env` проверяется по правам доступа, а не по содержимому.
- **Не дошли до OSV — ошибка, а не «чисто».** Пустой список находок от аудита,
  который не связался с базой, читался бы как здоровый проект.
- **Границы:** подкаталог проверяется по разрешённому пути внутри рабочего каталога,
  симлинки не обходятся, вывод ограничен `MAX_FINDINGS`.
- Публичному каналу эти инструменты недоступны (вне `PUBLIC_CHANNEL_CEILING`).

## Журнал ранов

Файлы: `backend/run_journal.py`, схема — в `backend/database.py` (оба диалекта).

- Ход записывается **до** обращения к провайдеру. Крах в середине оставляет
  запись, а не догадку.
- Незакрытые раны (`submitted` / `running`) на старте процесса переводятся в
  `interrupted`: задача, которой они принадлежали, ушла вместе с процессом.
  `reconcile_interrupted_runs()` идемпотентна.
- `user_text` очищается при закрытии рана: пока ход под угрозой — журнал его
  хранит, после — владельцем транскрипта становится таблица `messages`, и вторая
  копия пользовательского текста без владельца не нужна.
- Все записи best-effort: сбой журнала логируется, но **не** роняет ход.

## Схема БД

Файл: `backend/database.py`.

- Схема существует в **двух** функциях — `_init_sqlite_schema` и
  `_init_postgres_schema`. Новую таблицу нельзя копировать в обе руками: DDL
  описывается один раз в модуле-владельце и рендерится под диалект
  (`run_journal.schema_statements`, `shares.init_schema`). Две скопированные
  вручную схемы разъезжаются — это вопрос времени.
- Миграции только аддитивные: `ALTER TABLE ... ADD COLUMN` в `try/except
  OperationalError`, без удаления колонок.

## Настройки и модели

- **`app_settings` в БД перекрывает переменные окружения.** Правка
  `docker-compose.yml` в одиночку молча ничего не меняет.
- Значения в `app_settings` пишутся двумя разными кодировками; читатель обязан
  уметь оба варианта (`get_setting` декодирует строки, но не dict/list).
- **Модель и её endpoint ходят парой.** Взять одно без другого — это
  `HTTP 404` от провайдера. Смена модели затрагивает несколько мест, включая
  `.env`; убедись, что изменил их все.

## Простой чат: настройки чата, @агенты, ветки, инкогнито, арена

Файлы: `backend/chat_settings.py`, `backend/chat_arena.py`, `backend/agent.py`
(`_CHAT_SETTINGS`, `_AGENT_OVERRIDE`), `backend/main.py` (`/api/history/{id}/settings`,
`/api/history/{id}/fork`, `/api/chat/arena`, кадр `chat_message.agent_id`);
фронтенд — `frontend/src/components/simple/*`, `SimpleChatView.tsx`.

- **Настройки чата действуют только на свой ход.** Они ставятся в ContextVar на
  время `respond()` и читаются через свойства `temperature`, `max_tokens`,
  `local_think` — как выбор модели (`_LLM_OVERRIDE`). Записать их в атрибуты
  агента значит отдать температуру одного чата всем остальным разговорам.
- **Промпт чата дописывается, а не заменяет.** Системный промпт агента несёт
  правила инструментов, безопасности и обращения; `_chat_system_addendum()`
  добавляется после него в обоих местах сборки system-сообщения.
- `max_tokens` чата ограничивает только обычные ответы. Ходы с инструментами
  остаются на `tool_max_tokens`: короткий лимит обрезает сам вызов инструмента.
- **@упоминание переводит на другого агента ровно один ход.** `_AGENT_OVERRIDE`
  читается в `_respond` один раз и сразу сбрасывается, чтобы делегирование ниже
  по дереву выбирало агента по своей сессии. Неизвестный id молча откатывается
  на агента сессии (`_resolve_turn_agent`), ход не падает. Ответ подписан:
  `agent_id`/`agent_name` в `run_meta` (в `_PERSISTED_RUN_META_KEYS`).
- **Инкогнито не оставляет следов:** скрыт из `/api/history/sessions`, ход не
  извлекает долговременную память, при старте `purge_ephemeral_sessions`
  удаляет сообщения; фронтенд удаляет такой чат, как только с него ушли.
- **Ветка копирует чат до сообщения включительно** вместе с агентом, проектом и
  настройками. Без тела запрос по-прежнему копирует весь чат.
- **Арена — обычный completion, не ход агента:** без инструментов, истории и
  памяти. Ход агента может действовать, и сравнение формулировок выполнило бы
  действие дважды. Модели идут по очереди; клиент называет id каталога, не endpoint.
- `chat_settings` берёт путь к БД из `database.DB_PATH` при каждом подключении,
  потому что `respond()` читает настройки на каждом ходу: тест, подменивший БД,
  иначе писал бы в рабочий каталог данных.

## Загрузки и артефакты

Файл: `backend/media_snapshots.py`.

- Имя файла от клиента никогда не подставляется в путь: сначала
  `safe_filename`, затем `resolve_within` **по разрешённому пути** (`..` и
  симлинки разрешает файловая система, текстовая проверка их не ловит).
- Перезапись файла тем же именем сохраняет прежние байты в
  content-addressed снимок: файлы отдаются по имени, и перезапись иначе меняет
  то, что показывают уже существующие сообщения в чате.
- Опубликованные сайты dev-run'ов: одна неизменяемая директория на ревизию плюс
  один стабильный симлинк на цепочку (`backend/dev_sandbox.py`). URL, который
  владелец разослал, не меняется при доработке, а откат — это подмена симлинка.

## Публичные ссылки на диалог

Файл: `backend/shares.py`.

- Share — это **неизменяемый санитизированный снимок**, а не живое представление.
  Повторное открытие ссылки не может показать больше, чем было на момент создания.
- Публикуемые роли — allowlist (`user`, `assistant`). Роль, добавленная позже,
  по умолчанию не публикуется.
- Публикуемые поля сообщения — тоже allowlist (`role`, `content`, `ts`): новая
  колонка в `messages` не утечёт сама собой.
- Отзыв **удаляет** снимок. Отозванная ссылка перестаёт работать, а не просто
  исчезает из списка.
- Отозванная и никогда не существовавшая ссылка отвечают одинаково — иначе по
  ответу можно перебирать, какие токены были валидны.
- API публикации выполняет локальный privacy pass до создания снимка; отказ
  не публикует ничего. Legacy version=1 не открывается, но может быть отозвана.
  Плейсхолдеры секретов не публикуются; загрузки/инструменты/system роли исключены.
- Страница рендерится на сервере без JS и без внешних ресурсов: у опубликованного
  транскрипта нет пути обратно в приложение.

## Диагностика и падения

Файлы: `backend/crash_visibility.py`, `backend/request_diagnostics.py`.

- Watchdog медленных запросов — **один** поток на процесс. Таймер на каждый
  запрос упирается в лимит потоков под нагрузкой от поллинга и превращает
  проблему задержек в отказ приёма соединений.
- Зависший запрос отчитывается **один раз**, а не на каждом тике: иначе дамп
  стеков всех потоков хоронит тот лог, который должен помочь.
- Долгоживущие воркеры запускаются через `crash_visibility.spawn`, а не
  `asyncio.create_task`: у задачи, которую никто не ждёт, исключение всплывает
  только при сборке мусора, то есть для переменной уровня модуля — никогда.
- Любой хук логирования обязан глотать собственные ошибки: падающий хук сам
  становится новым способом потерять отчёт о сбое.

## Фронтенд

- Каталог `frontend/src/navigation/routes.ts` задаёт шесть рабочих зон и ссылки
  на канонические страницы. Старые `#tab=...`, история Back/Forward, разделы
  настроек, inbox alias сохраняются. SMM view и approval filter входят в hash.
- Новая навигация не создаёт вторую БД задач/агентов. Единые данные остаются у
  существующих страниц. Входящие рядом с клиентами, интеграции — отдельный вход.
- Центр подтверждений показывает arguments/diff до approval. full недоступен;
  тексты auto не обещают снять исходящие approvals. Повторный вход проходит
  через общий ReauthDialog, оригинальный Request повторяется только один раз.

- Ответ API проверяй на форму до того, как класть в состояние: payload ошибки —
  это объект, и `.map` по нему обнуляет весь дашборд.
- Все вызовы идут на относительные пути. Захардкоженный `localhost:8000` молча
  не работает в проде; охраняется `tests/urls.test.ts`.
- Vitest: фиксируй только дату (`toFake: ['Date']`). Полные фейковые таймеры
  подвешивают любой `waitFor` / `findBy`.
- Выпадающие списки внутри прокручиваемого контейнера — `position: fixed`,
  иначе контейнер их обрезает.
- Service worker **никогда** не кеширует `index.html` и навигацию: закешированная
  оболочка — это ровно то, как старый бандл переживает деплой.

## Развёртывание

- См. `docs/security-deployment.md`, `ops/security_preflight.py`. Только внешний
  data volume с проверенной миграцией, TLS, защищённый Valkey и runsc.
- Actions закреплены на commit SHA, минимальные permissions. CI проверяет код,
  тесты, секреты/OSV, образы и SBOM. Manual release сканирует тот же образ,
  который публикует, и подписывает digest + SBOM через keyless Cosign.
  Наличие workflow не доказывает, что удалённый CI уже прошёл.

- Прод может отставать от репозитория: сравнивай деревья до выкладки, а не после.
- Деплой, который «ничего не изменил», сначала проверяется по access-логу на
  предмет `GET /` — и только потом диагностируется дальше.

## Метрики сервера (вкладка «Метрики»)

Файлы: `backend/host_metrics.py`, `backend/tools.py` (`_read_host_telemetry`),
`frontend/src/components/metrics/*`; сборщик на хосте — `deploy/hermes-host-telemetry.py`
(вне репозитория).

- **Источник один — снимок хост-агента.** Агент пишет `data/host-telemetry.json`
  каждые 5 с; бэкенд не ходит в `/proc`/`nvidia-smi` хоста сам. Новые поля снимка —
  только аддитивные (`schema_version` остаётся 1), фронтенд обязан переживать их
  отсутствие у старого агента.
- **История — отдельная БД `data/host-metrics.db`, не `hermes.db`.** Сэмпл раз в 30 с,
  хранение 7 дней. Устаревший снимок (> 30 с) не записывается: иначе остановленный
  агент рисовал бы ровную линию поверх простоя.
- **Дыры не заполняются.** Пропуск в данных — разрыв линии на графике и алерт
  `telemetry_gap`, а не интерполяция.
- **Алерты структурные** (`kind`, `gpu`, `peak`, `threshold`): текст формирует фронтенд
  на языке пользователя. Пороги живут в `host_metrics.py` и отдаются в ответе.

## Autonomous Earner

Файлы: `backend/earner/*` (store, approvals, budget, llm, egress, scout, stages,
sandbox, repo, submit, worker, api), `frontend/src/components/earner/*`; подробно —
`docs/autonomous-earner.md`.

- **Подтверждение — серверный конечный автомат, не кнопка.** Привязано к
  (действие, цель, sha256 точного содержимого), истекает, одноразовое, гасится в
  той же транзакции `BEGIN IMMEDIATE`, что ставит стадию в очередь. Воркер перед
  стартом стадии ещё раз сверяет хеш. Новый путь, ставящий стадию в очередь в
  обход `approvals.confirm`, ломает границу.
- **`confirm` — только сессия оператора с `earner.approve`** и заголовок
  `X-Hermes-Intent`. Никакого сервисного ключа и внутреннего вызова; агентским
  инструментам Earner не виден (`test_no_agent_tool_or_stage_can_reach_approvals`).
- **Стадии — вызовы модели без tools.** Внешние тексты и ответ модели —
  данные; решения (статусы, «оплата подтверждена» = всегда false, допустимость
  артефакта) принимает серверный код.
- **Локальная модель по умолчанию; внешняя — только явно и с деньгами
  вперёд.** `earner/llm.py` отказывает нелокальному хосту для llama.cpp;
  внешняя модель (OmniRoute) — только при `external_enabled`, только с
  опубликованной ценой, с резервом долларов из месячного лимита до вызова и
  событием `external_model`. Что именно внешней модели разрешено (сразу для
  сложной задачи, повтор после отказа Reviewer, резерв) — часть подтверждения
  генерации и его хеша. Чатовые провайдеры (router tiers, agent providers) не
  используются.
- **Кошелёк — только приём.** Хранится публичный адрес; ключей, подписи и
  отправки транзакций в Earner нет. RPC-хосты и контракты токенов — код.
  Оплачено по блокчейну = привязанное поступление (`earner_income`).
- **Наружу — только текст, подтверждённый оператором.** Черновик комментария
  или PR собирается шаблоном (не моделью) и обязан содержать пометку об ИИ;
  `submit` привязан к точному тексту, а для PR — ещё к заголовку, ветке,
  сообщению коммита, хешам файлов и `artifact_hash`; правка аннулирует
  подтверждение, отправка одна, без повторов. Репозиторию, запрещающему вклад
  от ИИ, PR не создаётся.
- **Репозиторий задачи — данные.** Снимок одного коммита (codeload через
  egress, хосты — код), хранится архивом по sha256 и на диск backend не
  распаковывается; diff модели разбирается и применяется чистым Python (без
  удаления/переименования/CI/.git), `artifact_hash` покрывает снимок, diff,
  файлы и план тестов. Тесты репозитория — только `sandbox.run_repo` (runsc,
  без сети, вход через stdin); зависимости — из подготовленного образа.
- **Автопилот — тоже подтверждение оператора.** Грант `autopilot` (срок ≤30 дней,
  флаги `auto_generate`/`auto_execute`, план внешней модели) подтверждает
  человек; дальше `approvals.confirm_by_autopilot` гасит только generate/execute
  через тот же `_confirm_in_tx` (хеш, бюджет), actor = `autopilot:<грант>`.
  `submit` и кошелёк в `AUTOPILOT_ACTIONS` не входят и не должны. Kill switch,
  отзыв, истечение и любое изменение настроек останавливают грант. Включён по
  явному разрешению владельца 2026-10-20.
- **Бюджет резервируется до работы** условным UPDATE в `hermes.db`; не Qdrant и
  не Valkey. Начатая стадия после краха становится `interrupted` и не
  повторяется сама.
- **Сгенерированный код не исполняется в backend.** `ast.parse` — максимум.
  Исполнение — только `sandbox.run` с фиксированной спецификацией и `runsc`;
  `runc` как запасной вариант запрещён.
- **Интернет — только `earner/egress.py`:** точный allowlist, https:443,
  публичные адреса, закреплённый IP, без редиректов.
- Таблицы `earner_*` создаются `store.init_schema()` (только SQLite — как
  `agent_learning`); миграции аддитивные.
## Десктопы агентов (CLI-агенты по ACP)

Файлы: `agent_desktop/` (образ и мост внутри контейнера), `backend/agent_runtimes/`
(`acp.py`, `desktop.py`, `sessions.py`, `api.py`), записи `agent_desktop_*` в
`control_plane.TOOL_RISKS`, `frontend/src/components/desktops/*`.

- **Один агент — один изолированный Linux.** Контейнер `hermes-agent-desktop-<key>`
  из образа `hermes-agent-desktop:local`: X-дисплей, Chromium, терминал, закреплённые
  версии CLI. Домашний каталог (`AGENT_DESKTOP_HOST_ROOT/<key>/home`) — постоянное
  рабочее место агента: файлы, входы в CLI и профиль браузера переживают остановку.
- **Только gVisor.** Нет runtime `runsc` в Docker — десктоп не стартует. Тихого отката
  на runc нет; runc только при явном `AGENT_DESKTOP_ALLOW_RUNC=true` (машина разработки).
  Корень только для чтения, все capabilities сняты, лимиты памяти/CPU/pid, сети —
  как у dev-runner, никогда не сеть docker-proxy.
- **Сети подключаются до старта.** gVisor собирает сетевой стек один раз при старте:
  сеть, подключённая к работающему десктопу, внутри не появляется. Отсюда
  `containers.create` → `networks.connect` → `start`, а не `run`.
- **DNS — свой `resolv.conf` с публичными резолверами** (`AGENT_DESKTOP_DNS`).
  Встроенный DNS Docker держится на iptables в netns контейнера, которые gVisor не
  применяет. Побочный эффект — нужный: из десктопа не резолвятся внутренние имена.
- **OpenCode получает конфиг «ask»** для `edit`/`bash`/`webfetch` при создании дома
  (если файла ещё нет): по умолчанию он ничего не спрашивает, и Control Plane его
  действий не видел бы.
- **Ключ десктопа — слаг** `^[a-z0-9](?:[a-z0-9-]{0,30}[a-z0-9])?$`. Из него и только из
  него строятся имя контейнера и путь bind-mount; фронтенд проверяет то же правило.
- **У каждого десктопа свой токен** — HMAC ключа на `AGENT_DESKTOP_TOKEN_SECRET`.
  Нет секрета — нет десктопов. Мост не передаёт свой токен процессу агента.
- **Мост запускает только программы из таблицы `RUNTIMES`** (`agent_desktop/server.py`).
  Бэкенд выбирает имя, а не argv. Новый ACP-агент — строка там, строка в
  `sessions.RUNTIMES` и закреплённая версия в Dockerfile.
- **Hermes не предлагает агенту `fs` и `terminal`.** Агент работает своими
  инструментами внутри своего десктопа; любой другой запрос агент→клиент получает
  `-32601`.
- **Каждый `session/request_permission` — задача Control Plane** с инструментом
  `agent_desktop_<ToolKind>`. Режим автономии, одобрения, kill switch, бюджет команд и
  аудит работают как для своих инструментов. Неизвестный kind → `agent_desktop_unknown`
  → R4. Любой исход, кроме явного одобрения (отказ, kill switch, таймаут 15 мин,
  отменённый ход), — отказ агенту. `allow_always` не выбирается никогда: иначе агент
  перестал бы спрашивать.
- **То, что агент делает без вопроса, ограничено песочницей, а не Control Plane.**
  Сколько он спрашивает, решает сам CLI; граница безопасности — контейнер.
- **Браузер агента — видимый Chromium десктопа через Playwright MCP.** Каждая ACP-сессия
  получает MCP-сервер `browser` (`--cdp-endpoint` на CDP этого Chromium). Вызов MCP приходит
  как kind `other` с заголовком `browser_<tool>`: инструменты из `BROWSER_READ_TOOLS` —
  `agent_desktop_browser_read` (R1), из `BROWSER_ACT_TOOLS` — `agent_desktop_browser_act`
  (R2, как `execute`), прочие — `agent_desktop_other`. Chromium держится живым циклом в
  `start.sh`, `Singleton*` удаляются перед каждым запуском (иначе пересозданный десктоп
  получает профиль «занятый другим компьютером» и без CDP).
- **OpenCode спрашивает обо всём, включая MCP** — `"permission": {"*": "ask", …}` в
  управляемом конфиге (не в файле владельца): без этого вызовы MCP шли мимо Control Plane.
- **Ход — один за раз на (десктоп, рантайм).** Занятость ставится синхронно в
  `start_turn`, до запуска задачи: два запроса подряд не запускают два хода (409).
- **Прогресс — опрос журнала, не `/api/ws`.** Журнал на десктоп ограничен
  (`EVENT_LOG_SIZE`) и нумерован `seq`; клиент спрашивает `events?after=<seq>`.
  Журнал живёт в памяти процесса: рестарт бэкенда его обнуляет (персистентность —
  фаза 2).
- **Живой экран — VNC через бэкенд.** x11vnc слушает только loopback контейнера;
  `/api/agent-desktops/<key>/vnc` проверяет сессию из подпротокола `hermes-auth.` и
  право `agents.desktops.manage`, отвечает подпротоколом `hermes-vnc`. Отдельный
  location в nginx держит соединение до часа.
- **Локальная модель — через `/agent-llm/v1` бэкенда** (`llm_proxy.py`), никогда не
  напрямую к llama и не по `LLM_PROXY_TOKEN`. Токен — `<key>.<hmac>` из
  `desktop.llm_token` (домен `llm:`, отдельно от токена моста); путь вне `/api/` и не
  проксируется nginx — достижим только из сетей бэкенда. Каждый запрос ждёт в
  `llm_gate` с `PRIORITY_BACKGROUND` и держит слот до конца стрима; освобождение
  идемпотентно и висит и на `finally` стрима, и на background ответа. Одна модель,
  `max_tokens` ≤ `AGENT_LLM_MAX_TOKENS`, один запрос на десктоп (429).
- **Из сети песочниц — только `/agent-llm/`** (`net_guard.py`, самый внешний ASGI-слой).
  Решает интерфейс бэкенда, на который пришло соединение (`scope["server"]`), а не адрес
  клиента. С интерфейса dev-сети любой другой путь — 403 (WebSocket — close 1008), кроме
  шлюза сети (это хост); `/agent-llm/` с любого другого интерфейса — 403. Пока адреса не
  выяснены через docker-proxy, `/agent-llm/` закрыт везде, `/api` работает, повтор раз в 30 с.
- **Адрес бэкенда — запись `hermes-backend` в `/etc/hosts` десктопа**, IP бэкенда в
  общей с десктопом сети на момент создания. Сменился IP (бэкенд пересоздан) —
  работающий десктоп пересоздаётся при следующем `ensure`; остановленный десктоп
  всегда пересоздаётся, а не стартует (всё ценное — в доме).
- **Провайдер OpenCode — управляемый файл** `~/.config/hermes/opencode.json` через
  `OPENCODE_CONFIG`, переписывается при каждом создании; `~/.config/opencode/opencode.json`
  владельца не трогается. Токен — только в этом файле, не в env контейнера.
- **Тип десктопа — `agent` или `openbot`** (`desktop.KINDS`), записан файлом `<root>/<key>/kind` и
  переживает пересоздание; другой тип для того же ключа — отказ. Тип меняет образ, точку
  монтирования дома, uid, лимиты, число экранов и время остановки — **никогда** изоляцию
  (runtime, read-only, capabilities, сети, DNS, hosts, токен моста задаёт `_blocking_ensure`
  для всех). `openbot` — отдельный флаг `OPENBOT_DESKTOPS_ENABLED` (лицензия Noncommercial);
  ACP-ходы в нём отклоняются (422). Подробно и модель угроз — `docs/agent-desktops-openbot.md`.
- **Работающий десктоп пересоздаётся через `stop(timeout=<тип>)`, не `remove(force)`**:
  OpenBot закрывает базу до 60 с.
- **Экраны:** мост отдаёт `/vnc?screen=N` по `AGENT_DESKTOP_VNC_PORTS`; бэкенд пропускает
  только `N < screens` типа десктопа.
- **Модели OmniRoute в `/agent-llm`** — `omniroute/<id>` из `/v1/models` роутера, только при
  `AGENT_LLM_EXTERNAL_ENABLED`, по шаблонам `AGENT_LLM_EXTERNAL_MODELS`, с суточным лимитом $
  и запросов на десктоп по `router_usage_log` (`agent-desktop:<key>`). Каталог не прочитан —
  503, а не догадка. Ключ роутера в десктоп не попадает. Шлюз приватности не применяется.
- **Kill switch отключает `/agent-llm` целиком** (503 `killed`), ошибка чтения состояния — тоже
  отказ.
- **Вход в CLI — руками владельца в терминале десктопа** («Управлять» →
  `grok login` / `opencode auth login`). Ошибка `auth_required` приходит в событии
  `turn_end.error_code`, текст фронтенд берёт по коду.
