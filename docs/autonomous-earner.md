# Autonomous Earner

Раздел дашборда, который ищет небольшие программные задачи и баунти, оценивает
их, готовит решение и проверяет его в изоляции. Каждая стадия, которая тратит
время модели, открывает сеть или исполняет сгенерированный код, ждёт
подтверждения оператора на сервере. Отклики заказчикам, передача результата,
публикация и любые деньги остаются ручными.

Код: `backend/earner/` (пакет), `frontend/src/components/earner/`. Тесты:
`backend/tests/test_earner.py`, `frontend/src/components/earner/EarnerTab.test.tsx`.

## Пользовательский путь

1. **Настройки** — направления, ограничения, разрешённые хосты (точные имена),
   источники (`demo`, `github_issues`, `rss`) и дневные лимиты.
2. **Обзор → «Запросить исследование»** — сервер готовит экран подтверждения:
   что будет сделано, какие данные, какие лимиты, что не входит.
3. **Подтверждения → «Подтвердить»** (после галочки «Я проверил(а)…») —
   исследование ставится в очередь: Scout собирает кандидатов, Evaluator
   оценивает до N из них и готовит предложения.
4. **Возможности → карточка** — предложение, критерии приёмки, оценка
   трудозатрат, заявленная (не подтверждённая) награда. Отдельное подтверждение
   генерации.
5. Builder пишет код, тесты и README (только stdlib Python 3.11); Reviewer
   сверяет с критериями и может отклонить.
6. Оператор читает код в карточке и отдельно подтверждает исполнение этого
   артефакта (по его хешу).
7. Sandbox прогоняет `python -m unittest` в gVisor без сети; результат, ZIP и
   журнал — в карточке.
8. Передачу и оплату оператор отмечает вручную; только они попадают в отчёт
   как «передано» и «оплачено».

## Подтверждения

`backend/earner/approvals.py`. Действия: `research`, `generate`, `execute`,
`schedule`.

- Привязка к действию, цели и sha256 канонического содержимого, которое видел
  оператор. Срок — `EARNER_APPROVAL_TTL_MINUTES` (по умолчанию 60).
- `confirm` — одна транзакция `BEGIN IMMEDIATE`: статус `pending` → проверка
  срока → сверка хеша с экраном → пересчёт содержимого из живых строк и сверка
  → резерв бюджета → `consumed` и постановка стадии в очередь. Любой сбой
  откатывает всё; повтор и параллельный второй `confirm` получают 409.
- Изменение настроек аннулирует ожидающие `research`/`schedule` и останавливает
  расписание; изменённое предложение/артефакт аннулирует подтверждение при
  попытке подтвердить, а воркер ещё раз сверяет хеш перед стартом стадии.
- Подтверждать может только сессия оператора с правом `earner.approve`
  (по умолчанию только `owner`) и с заголовком `X-Hermes-Intent: earner-approve`.
  Сервисного ключа нет; агентские инструменты не держат сессию дашборда.
  Аутентификация — Bearer-токен, не cookie, поэтому CSRF-поверхности нет.
- Автопоиск по расписанию — отдельное подтверждение `schedule` с интервалом
  (6–168 ч), сроком (≤14 дней) и числом запусков; на генерацию и исполнение
  оно не распространяется.

## Источники задач

| Тип | Что читает | Разрешённый хост |
|---|---|---|
| `demo` | встроенная учебная задача | — |
| `github_issues` | поиск GitHub Issues (например `label:bounty language:python state:open`) | `api.github.com` |
| `rss` | любая RSS/Atom-лента; пресет — FL.ru «Программирование» (`https://www.fl.ru/rss/all.xml?category=5`) | хост ленты |
| `freelancer_com` | публичный API активных fixed-проектов Freelancer.com по запросу | `www.freelancer.com` |
| `freelancehunt` | публичный API Freelancehunt по id навыков (22 Python, 169 парсинг, 180 боты, 178 обработка данных) | `api.freelancehunt.com` |
| `opire` | награды Opire за GitHub-issues; текст задачи — через `api.github.com`, если он разрешён | `api.opire.dev` |
| `superteam` | Superteam Earn Agent API: открытые листинги `AGENT_ALLOWED`/`AGENT_ONLY` верифицированных спонсоров (`GET /api/agents/listings/live`), описание — `GET /api/agents/listings/details/<slug>`; ключ агента `EARNER_SUPERTEAM_API_KEY` | `superteam.fun` |

**Крипто-площадки (исследование 2026-10-20).** Подключена только Superteam Earn: у неё документированный
Agent API, и правила прямо приглашают ИИ-агентов (агенту видны лишь листинги, открытые для агентов; выплату
получает человек через claim-code; лимит 60 отправок в час). Выплаты — USDC, обычно в Solana: наблюдатель
кошелька Earner видит только EVM-сети, такие поступления привязываются вручную. Регистрация агента —
вручную оператором (`POST https://superteam.fun/api/agents` с именем; ключ `sk_…` → «API-ключи»); Earner
только читает листинги, сдача работы на площадке — вручную. Не подключены: Algora (выплата USD через
Stripe — не стейблкоин; их задачи и так видны в GitHub Issues), Drips Wave (валюта и публичный API не
подтверждены, KYC), Bountycaster (нет документированного API), Code4rena/Immunefi/Sherlock (аудит
безопасности — вне возможностей Builder), агентские маркетплейсы на x402/escrow (ранние, без подтверждённых
выплат, требуют подписи кошельком — ключей в Earner нет).

Проверено 2026-10-20 с сервера. Без входа не читаются: Habr Freelance (ленты отключены, 410), Upwork и
Guru (403), Weblancer и freelance.ru (лент нет); Kwork отдаёт только HTML — его страницы не парсятся.
Лимит кандидатов на запуск делится поровну между источниками. Перед Evaluator — бесплатный отбор по
ключевым словам профиля (Python, скрипт, парсер, бот, API, CSV, Excel…) и «Направлениям»: кандидаты без
совпадений не оцениваются и не тратят вызовы модели. Отклик на биржах (Freelancer, Freelancehunt, FL.ru)
— вручную по ссылке из карточки; автоматическая отправка есть только для GitHub issues.

## Автопилот

Настройки → «Автопилот» → «Запросить разрешение автопилота» → подтвердить в
«Подтверждениях». Это одно разрешение на срок (до 30 дней): поиск по расписанию
(интервал от 2 ч, до 120 запусков) и — по флагам — автоподтверждение генерации и
исполнения в gVisor-песочнице. Каждое автоподтверждение проходит те же проверки
(хеш содержимого, дневной бюджет), что и ручное, и записано в журнале от имени
гранта. Не покрывает отправку заказчикам и кошелёк. Останавливается кнопками
«Остановить автопилот» / «Остановить Earner», по сроку и при любом изменении
настроек Earner (тогда нужен новый грант).

## Модель

`backend/earner/llm.py`: по умолчанию llama.cpp из `LLAMACPP_BASE_URL`
(`EARNER_LLAMACPP_BASE_URL` переопределяет), модель `LLM_MODEL` (`EARNER_MODEL`).
Нелокальный хост → отказ.

**Внешние модели** (Настройки → «Внешние модели») — через OmniRoute
(`ROUTER_API_BASE`, ключ `ROUTER_API_KEY` из «API-ключей»). Только модель с
опубликованной ценой в `/v1/models`; стоимость `(оценка промпта × цена входа +
max_tokens × цена выхода) × 1.2` резервируется из месячного лимита
(`external_month_usd`, по умолчанию $30, максимум $200) до вызова и после ответа
заменяется фактической. Когда используется: Builder сразу — если Evaluator
оценил задачу больше чем в 1 час или с неопределённостью выше «low»; одна
повторная генерация с замечаниями Reviewer после отказа; резерв, если локальная
модель недоступна или ответила неверно. Это записано в подтверждении генерации
(и в его хеше); смена модели или лимита аннулирует ожидающие подтверждения.
Каждый внешний вызов — событие `external_model` и строка в «Истории и
расходах» с ценой. Вызовы идут через
`backend.llm_gate` с `PRIORITY_BACKGROUND` (чат обслуживается первым, но
начатую генерацию llama.cpp не прерывает — при `--parallel 1` чат ждёт её
окончания), по одному за раз, `think=False`, без tools, без повторов.
Глобальные настройки модели не меняются.

## Интернет

`backend/earner/egress.py`: выключен, пока нет разрешённых хостов. Только
`https://` на 443, точное совпадение имени, все адреса из DNS — публичные,
соединение — к проверенному адресу (без повторного резолва), без редиректов,
≤512 КБ, ≤15 с, лимиты на запуск и на сутки. Платные поисковые сервисы не
подключены.

## Бюджет

`backend/earner/budget.py`, таблицы в `hermes.db`. Значения по умолчанию:
5 задач, 20 вызовов модели, 100 000 токенов резерва, 60 запросов к источникам,
10 запусков sandbox в сутки (UTC); sandbox — один одновременно. Резерв —
атомарный условный UPDATE до начала работы; токены резервируются как
`символы/3 + max_tokens` и после ответа уменьшаются до фактических. Денежная
цифра — оценка электричества (`EARNER_LOCAL_WATTS`, `EARNER_KWH_PRICE_USD`), не
оплата.

## Кошелёк и доход

`backend/earner/wallet.py`. В настройках — только публичный EVM-адрес и сети
(Base, Polygon, Ethereum). Раз в 5 минут воркер читает события `Transfer`
контрактов USDC/USDT на этот адрес через публичные RPC (хосты и контракты — в
коде, проверены on-chain), с запасом подтверждений (Base 30, Polygon 64,
Ethereum 12 блоков). Каждое поступление — строка `earner_income` (повтор
невозможен). Автопривязка к задаче — только если ровно одна переданная и
неоплаченная задача заявляет эту сумму (±1 %); иначе оператор привязывает во
вкладке «Доход». Ключей, подписи и отправки с кошелька в Earner нет.

## Режим репозитория (GitHub issue → патч)

`backend/earner/repo.py`, `stages.py` (Locator, Builder, Reviewer для diff), `sandbox.run_repo`.
Если задача — issue публичного Python-репозитория на GitHub, Evaluator получает пометку «доставка — патч»
(`proposal.delivery = repo_patch`, решает сервер по URL, не модель), и после подтверждения генерации:

1. **Снимок.** Три запроса через egress к коду-фиксированным хостам `api.github.com` и
   `codeload.github.com`: метаданные (публичный, не архивирован, не переименован), SHA коммита ветки по
   умолчанию, архив **именно этого коммита** (≤ `EARNER_REPO_MAX_MB`, 20 МБ). Архив хранится одним файлом
   `<sha256>.tar.gz` в `data/earner/repos/` (`EARNER_REPO_CACHE_DIR`), удаляется через 14 дней. На диск
   backend он **не распаковывается**: дерево читается в памяти (`tarfile`), только обычные файлы с
   безопасными путями (симлинки, хардлинки, устройства, `..`, `.git` отбрасываются), ≤ 8000 файлов,
   ≤ 80 МБ. Распаковка — только внутри gVisor.
2. **Правила репозитория.** CONTRIBUTING/AGENTS/README/CODE_OF_CONDUCT проверяются на запрет вклада от ИИ —
   при запрете стадия останавливается до вызова модели; просьба указывать ИИ запоминается.
3. **Контекст.** Locator (≤ 500 токенов ответа) выбирает файлы по списку путей; сервер добавляет файлы,
   названные в issue, файлы с идентификаторами из issue и их тесты. Модель видит ≤ `EARNER_REPO_CONTEXT_KB`
   (40 КБ) кода: маленькие файлы целиком, большие — окнами с номерами строк.
4. **diff.** Builder возвращает unified diff. Сервер разбирает его строго: только правки и новые файлы
   (без удаления, переименований, смены режима, бинарных патчей и симлинков, без `.git`/`.github`/CI),
   ≤ 12 файлов, ≤ 96 КБ; применяет чистым Python по точному совпадению контекста (допуск — пробелы в конце
   строк, контекст остаётся из файла); изменённые `.py` проверяются `ast.parse`. Хранится канонический
   diff (difflib от результата) — его видит оператор и его же несёт PR. «На что посмотреть»: запуск
   процессов, сеть, eval, секреты, новые внешние адреса, правки сборки/зависимостей/conftest, отсутствие
   тестов. Если diff не применился и разрешена внешняя модель — один повтор с точной причиной.
5. **Хеш.** `store.artifact_hash` патча = снимок (owner, repo, ветка, коммит, sha256 архива) + diff +
   файлы после правки + план тестов. Подтверждения execute и submit привязаны к нему; экран execute и
   submit показывает сам diff.
6. **Тесты.** `sandbox.run_repo`: тот же gVisor без сети, монтирований и секретов; 2 CPU, 2 ГБ, 256 PID,
   tmpfs 1 ГБ noexec, ≤ `EARNER_REPO_SANDBOX_TIMEOUT` (240 с) на прогон. docker-socket-proxy не разрешает
   ни тома, ни сборку образов, а архив не помещается в переменную окружения, поэтому вход идёт через stdin
   контейнера (attach): длина + JSON-план + длина + архив. Bootstrap распаковывает архив, прогоняет тесты
   на исходном коммите (baseline, `EARNER_REPO_BASELINE`), накладывает файлы патча и прогоняет снова.
   Раннер выбирает сервер (pytest при pytest.ini/conftest/`[tool.pytest]`, иначе unittest) — не
   репозиторий и не модель; `--continue-on-collection-errors`; если addopts репозитория требуют плагин,
   которого нет в образе (pytest завершился до отчёта junit: `--cov` → код 4, `-p плагин` → код 1), — один
   повтор без addopts. Итог: `passed` — набор с патчем зелёный;
   `no_regressions` — каждое падение было и без патча, тестов не стало меньше, и тесты, которые добавил или
   изменил сам патч, прошли; иначе `failed`. Оба первых статуса = «проверки пройдены».

**Зависимости — решение.** Сеть в песочнице не открывается ни на каком шаге. Используется заранее
подготовленный кэш: образ `hermes-earner-runner:local` из `backend/earner/runner/` (точные версии, только
wheels — при сборке не исполняется код пакетов). Включение: `docker build -t hermes-earner-runner:local
backend/earner/runner` и `EARNER_REPO_SANDBOX_IMAGE=hermes-earner-runner:local`; без него используется
`EARNER_SANDBOX_IMAGE` (dev-runner, в нём есть pytest). Объявленные зависимости репозитория читаются как
данные (requirements*.txt, pyproject через tomllib) и сверяются внутри песочницы с установленными —
недостающие показываются в карточке. Отдельный шаг «pip с allowlist PyPI» не сделан сознательно: установка
sdist исполняет код пакета, разрешение версий — это pip внутри песочницы с сетью, а сеть для контейнеров
потребовала бы egress-прокси на новой сети Docker; при `no_regressions` недостающая зависимость видна как
падение и на исходном коммите.

## Отправка заказчику

`backend/earner/submit.py`. Для задачи из GitHub issue, прошедшей проверки в sandbox, — два вида:

- **Комментарий** — шаблон (решение или diff, результат тестов, предложение открыть PR, пометка об ИИ).
- **Pull request** (для патча к репозиторию) — шаблон «Fixes #N», что изменено, результат тестов (с
  честной оговоркой при `no_regressions`), пометка об ИИ. Отправка через Git Data API, без `git push`:
  форк от имени владельца токена (или существующий), один коммит ровно с подтверждёнными файлами поверх
  закреплённого коммита, ветка `hermes/issue-N-…`, PR из форка в ветку по умолчанию,
  `maintainer_can_modify`. Перед отправкой каждый файл сверяется с хешами из подтверждения, артефакт — с
  хешем; любое расхождение — «не отправлено». ≈ 8 запросов к `api.github.com`, без повторов.

Оператор может отредактировать текст (и заголовок PR); правка аннулирует ожидающее подтверждение, а
текст без пометки об ИИ нельзя ни сохранить, ни подтвердить. Подтверждение `submit` привязано к точному
тексту, заголовку, ветке, сообщению коммита, хешам файлов и хешу артефакта; `submit` не входит в
автопилот. Репозиторию, запрещающему вклад от ИИ, PR не создаётся. Токен `EARNER_GITHUB_TOKEN`
(Настройки → API-ключи) — **classic со scope `public_repo`**: fine-grained токены по документации GitHub
не могут писать в публичные репозитории, где вы не участник (ни PR, ни, вероятно, комментарии).

## Исполнение

`backend/earner/sandbox.py`. Брокер — этот модуль внутри backend, через
существующий docker-socket-proxy. Спецификация фиксирована: `runtime=runsc`,
`network_mode=none`, без томов и устройств, uid 10001, `cap_drop=ALL`,
`no-new-privileges`, rootfs только чтение, tmpfs 64 МБ noexec, 1 CPU, 512 МБ
(swap включён в лимит), 64 PID, nofile 256, fsize 16 МБ, лог 256 КБ,
таймаут `EARNER_SANDBOX_TIMEOUT` (60 с). Файлы передаются данными в одной
переменной окружения; команда — постоянный bootstrap. Без runtime `runsc`
исполнение недоступно (подтверждение не создаётся); `runc` настроить нельзя.

### Включение gVisor (требует отдельного решения владельца)

Установка затрагивает Docker daemon хоста:

1. Установить `runsc` из официального репозитория gVisor
   (https://gvisor.dev/docs/user_guide/install/).
2. Добавить runtime в `/etc/docker/daemon.json`
   (`runsc install` делает это сам) и перечитать конфигурацию
   (`systemctl reload docker` — SIGHUP; перечитывание runtimes не перезапускает
   контейнеры, но проверьте поведение вашей версии Docker).
3. Проверить: `docker info --format '{{json .Runtimes}}'` содержит `runsc`;
   `docker run --rm --runtime=runsc --network none <образ> python -c 'print(1)'`.
4. В разделе «Обзор» строка «Исполнение» станет «доступно».

## Остановка и откат

- Остановить: кнопка «Остановить Earner» (новые стадии не запускаются) или
  `EARNER_ENABLED=false` в окружении backend и перезапуск backend (воркер не
  стартует; API и данные остаются).
- Исполнение отдельно: `EARNER_EXECUTION_ENABLED=false`.
- Откат кода: вернуть предыдущий образ backend/frontend. Таблицы `earner_*`
  аддитивны и другим кодом не читаются; их можно оставить.

## Известные ограничения окружения

- docker-socket-proxy разрешает `POST /containers/create` с любым телом. Тот,
  кто управляет процессом backend, уже может создать привилегированный
  контейнер — Earner этого не расширяет, но и не устраняет.
- Владельческий агент с подтверждённым R4 `execute_command` выполняет shell
  внутри backend: оттуда читаются `.env` и БД, и записи `earner_approvals`
  можно подделать напрямую. Граница подтверждений защищает от стадий Earner,
  страниц и агентов без shell, но не от процесса backend целиком.
- Статический dev-runner получает весь `.env` и выход в интернет, работает на
  runc — для недоверенного кода Earner он не используется.
- Ключи (`ROUTER_API_KEY`, `EARNER_GITHUB_TOKEN`) лежат в таблице `api_keys`
  hermes.db открытым текстом — их читает всё, что читает БД backend.
- Режим репозитория поддерживает только Python-репозитории; JS/Go/Rust-задачи Evaluator отклоняет, а
  Builder останавливается на снимке.
- Bootstrap репозиторного режима проверен в одноразовом контейнере без сети (runc, образ dev-runner);
  передача через attach к stdin под gVisor через docker-socket-proxy проверяется при выкладке (запуск
  контейнера с доступом к Docker API на проде требует отдельного разрешения).
- Результат тестов формирует код внутри песочницы, то есть и код репозитория (например, conftest);
  это свидетельство для оператора, не граница безопасности.
